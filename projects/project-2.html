Cross-Project dbt Dependencies on AWS MWAA

Professional Project · Data Engineering · Published on DEV Community, November 2024

Read the full article on DEV

The final design described in the article.

Overview

A technical article I wrote and published on DEV Community about running multiple dbt projects on Amazon Managed Workflows for Apache Airflow (MWAA), where models in one project depend on models in another. It walks through a failed first attempt, the workaround that worked, and the trade-offs.

The Problem

Splitting a large dbt project into smaller ones keeps teams independent, but the child projects still need to reference shared models from a parent project. The usual approach, pulling the parent from a private Git repository with dbt deps, failed inside MWAA with a Permission denied (publickey) error, and storing the SSH key in AWS Secrets Manager did not fix it.

My Approach

  1. Provisioned MWAA with Terraform. I used the aws-ia/mwaa/aws module and linked S3 paths for DAGs, requirements, a startup script and plugins.
  2. Tried a virtual environment first. A PythonVirtualenvOperator task ran dbt deps and dbt run, with the parent project listed as a Git package. This hit the SSH authentication error.
  3. Packaged the parent project as a plugin. I zipped the parent dbt project into plugins.zip, so MWAA copies it onto every Airflow worker.
  4. Pointed the child project at the local copy. The child project’s packages.yml references the parent with a local: path, so no Git access is needed at run time.
  5. Documented the trade-offs. The approach adds CI/CD steps, and I suggested KubernetesPodOperator as an alternative worth comparing.

Tools and Technologies

Impact

Removed the need for SSH keys at run time, kept the parent project’s models and macros available locally on Airflow, and gave a pattern that scales to more dbt projects and can be automated with Terraform and CI/CD. Sharing it publicly helps other data engineers who run into the same MWAA limitation.

Connection to AI

Machine learning teams depend on shared, well-tested data models, often owned by different teams. Reliable cross-project dependencies mean a feature table used by a model is built from the same trusted definitions as every report, which is the kind of consistency trustworthy AI needs.
